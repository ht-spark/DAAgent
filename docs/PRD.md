### 1. 背景与目标

#### 1.1 背景

当前企业数据分析的主要问题并不只是工具使用门槛高，而是整个分析链路存在割裂、重复劳动和协作成本，具体表现为：

1. **业务问题难以转化为分析问题**：用户往往知道自己关心什么，却难以明确指标口径、对比基准、分析维度和验证方法。
2. **数据查找与获取成本高**：表、字段和数据文档数量多且信息不完整，分析师需要反复找数据、确认关联关系并编写或修改取数代码。
3. **指标口径缺乏统一管理**：同一指标可能存在多种定义，造成跨部门结果不一致，并增加沟通、核验和决策风险。
4. **数据处理占用大量时间**：缺失、重复、异常和延迟等问题依赖人工清洗与校验，真正用于分析判断的时间被持续压缩。
5. **探索式分析响应缓慢**：产品经理和业务运营提出新的维度或原因假设后，通常需要重新向分析师提需求、等待取数并再次分析。
6. **现有工具偏重展示而非解释**：传统 BI 和固定看板擅长回答“发生了什么”，但难以持续下钻并回答“为什么发生、下一步怎么办”。
7. **单点智能能力无法覆盖完整流程**：Text-to-SQL 主要解决取数问题，Notebook 和脚本则依赖专业能力，均未完整覆盖问题澄清、数据处理、探索验证、结论追溯和报告交付。
8. **业务知识与历史分析难以复用**：指标定义、业务说明和历史结论分散在不同文档中，分析时容易缺少上下文，相似问题也需要重复处理。
9. **分析结果与业务决策之间仍有距离**：许多分析止步于指标和图表，未形成从异常发现、原因解释到行动建议的完整链路。

基于以上问题，数据分析产品需要从“数据查询与展示工具”升级为“面向业务问题的分析执行系统”：以具体问题为起点，连接数据、业务知识和分析过程，完成从问题澄清、数据处理、探索验证到结论表达的闭环，并允许用户在关键节点介入和核验。

#### 1.2 目标

- **降低分析门槛与交付周期**：用户提交业务问题和数据文件后，系统自动完成数据理解、清洗、分析、验证与报告生成，减少对 SQL、Python 和统计工具操作经验的依赖。
- **提升分析深度**：不止返回指标和图表，而是围绕业务问题进行趋势、对比、分群、归因等探索，形成从现象、证据到原因解释和行动建议的完整分析链路。
- **保证过程可控、结果可信**：在信息不足、分析预算和最终交付等关键节点支持人工介入；保留中间代码、数据、决策日志和审查结果，使关键结论可复现、可核验、可追溯。
- **统一并复用业务知识**：通过知识库沉淀指标口径、业务说明和历史分析，为任务提供可引用的上下文，减少重复确认和口径冲突。
- **逐步形成分析知识闭环**：在当前任务执行与知识检索能力的基础上，后续打通知识加载、任务产出回灌和多轮追问，使一次性分析逐步演进为可持续复用的组织分析能力。

### 2. 产品概述

#### 2.1 产品定位

DAAgent 是一款面向业务问题的自动化数据分析 Agent。用户以自然语言问题和数据文件发起分析任务，并可通过知识库先行核对业务资料；系统由大模型围绕当前问题自主规划分析路径，调用代码完成数据处理与验证，最终交付包含图表、结论、证据和审查信息的完整报告。

产品当前以“文件驱动的端到端分析”为核心：重点解决从已有数据到可信分析交付之间的效率与质量问题，而不是替代企业数据仓库、指标平台或实时 BI。其差异化不在于把自然语言直接翻译成 SQL，也不在于套用固定分析模板，而在于依据具体问题和数据特征动态完成 **“理解问题 → 处理数据 → 探索验证 → 解释结果 → 生成报告”**，并通过质量门和中间产物让过程可监控、可干预、可复现。

产品将沿着“自动完成一次分析 → 接入并复用业务知识 → 支持连续追问与自动下钻 → 关联更多业务上下文”的路径演进，最终帮助用户从数据变化定位关键原因，并将分析结果转化为可执行的决策依据。

#### 2.2 目标用户

| 用户类型       | 典型痛点                                          | 核心诉求                                         |
| -------------- | ------------------------------------------------- | ------------------------------------------------ |
| 产品经理       | 不擅长直接取数，新的分析思路依赖分析师再次排期    | 用业务语言发起分析，快速获得可继续验证的原因解释 |
| 数据分析师     | Ad-hoc 需求多，反复找数据、清洗、改代码和制作报告 | 自动完成重复环节，把时间集中在方法判断与业务解释 |
| 业务运营/增长  | 关注转化、留存和活动效果，但缺少独立分析能力      | 从指标变化快速定位关键维度并获得行动建议         |
| 数据团队负责人 | 指标口径不一致，历史分析难复用，结论过程难以追溯  | 规范分析交付，沉淀可核验、可复用的分析资产       |

#### 2.3 核心场景

1. AB测试
2. 竞品分析
3. 需求调研
4. PRD文档撰写
5. 日报、周报、月报、季报、年报
6. 日常数据分析（漏斗分析、DAU、GMV、因果推断、归因分析、指标体系构建等）

### 3. 需求说明

#### 3.1 功能需求

##### 3.1.1 提交任务

- **FR-001**：用户可提交自然语言分析问题文本，或上传 `.md`/`.txt` 问题描述文件。
- **FR-002**：用户可附加数据文件（CSV/Excel/JSON/Parquet 等，可多个）。
- **FR-003**：用户可选择/配置大模型（OpenAI、DeepSeek 或自定义 OpenAI 兼容 endpoint）。
- **FR-004**：提交后启动进程内后台任务，返回运行 ID，支持事件重连；持久化队列仍属规划。

##### 3.1.2 运行中的人工介入

- **FR-005**：若问题或数据信息不足（G0 摄入门），系统弹出澄清请求（如：主键是什么、时间范围、成功指标定义），用户可终止或补充材料。
- **FR-006**：每个子问题可弹出预算确认（沿用默认或覆盖上限），用户可调整每步的分析预算。
- **FR-007**：用户可随时取消任务，系统停止后续执行并保留已产出的中间产物。

##### 3.1.3 进度与产物

- **FR-008**：系统通过 NDJSON 流推送规划、Todo、动作、观察、审批、回答及完成事件；完成事件提供 `trace_id` 和 `usage_summary`，未知用量为 `null`。
- **FR-009**：任务完成后，用户可获取完整产物包：
  - 分析报告（Markdown / DOCX）
  - 图表（趋势、对比、分布、漏斗、留存、相关性等业务分析图）
  - 表格（汇总统计、分组结果、显著性检验）
  - 中间代码与清洗后数据
  - 审查报告（数据质量、方法合理性、结论风险）

##### 3.1.4 关键能力

- **FR-010**：自动分析路径探索——结合问题类型与数据特征，选择描述统计、对比分析、归因拆解、相关/回归、漏斗与留存等方法，避免「拍脑袋下结论」。
- **FR-011**：代码化分析——LLM 生成 Python 分析代码并在隔离子进程执行，结果可复现。
- **FR-012**：按问题类型校验——描述/对比/归因/预测/漏斗/异常检测等分别有对应的验证规则（如：样本量、混杂因素、显著性、业务合理性）。
- **FR-013**：可追溯报告——报告章节与证据、决策日志、各子问题结论一一对应，关键数字可回溯到中间表。

---

#### 3.2 非功能需求

##### 3.2.1 文档管理

- **FR-014**：用户可上传 PDF/DOC/DOCX/PPT/PPTX/PNG/JPG/Markdown/TXT 文件，或含上述文件的 ZIP 包。
- **FR-015**：非 Markdown 文档经 MinerU 自动转换为 Markdown（公式、表格可识别）。
- **FR-016**：用户可删除文档，系统同步删除向量并重建索引。
- **FR-017**：用户可查看已索引文档清单与切片数量。

##### 3.2.2 检索与问答

- **FR-018**：用户可在知识库中进行头脑风暴提问，获得带引用出处的回答（如：指标口径、历史结论、分析框架）。
- **FR-019**：检索采用混合检索（稠密 BGE 语义向量 + 稀疏 BM25 关键词）+ RRF 融合，各取 Top 5 片段。
- **FR-020**：每个回答附带 `source_file`（来源文档）与原文片段，便于用户核对。
- **FR-021**：可选 LLM 上下文压缩，去除冗余噪声。

##### 3.2.3 历史与统计

- **FR-022**：用户可查看历史头脑风暴讨论。
- **FR-023**：用户可查看知识库统计（文档数、切片数、索引状态）。

### 4. 上线与迭代

#### 4.1 当前版本范围（V1.0）

**已实现**：

- 统一 Plan-and-Execute 与 ReAct 数据分析流程，由 LLM 选择工具与分析路径
- 决策轮数、单 Todo 步数、重复调用拦截、失败熔断与有限恢复规划
- 知识库上传、转换、分块、嵌入、检索
- 头脑风暴问答与引用溯源
- FastAPI 后端 + React 前端
- NDJSON 实时事件、进程内后台运行、事件重连与用户取消
- 本地 span 树、模型真实 token 采集、可选单价估算、JSONL 与 SQLite 双写（P0-1）；独立验证器尚未接入

**暂未实现（规划中）**：

- 分析任务向知识库自动回灌与跨会话长期记忆（当前已支持可选知识库检索、多轮追问和滚动摘要）
- 独立验证器、三道质量门（G0/GQ/GF）、子问题预算确认与崩溃续跑
- 团队协作功能（共享任务、评论、审批流）

#### 4.2 迭代路线

| 版本 | 目标                                            |
| ---- | ----------------------------------------------- |
| V1.1 | 修复已知 bug，优化 prompts，提升报告质量        |
| V1.2 | 打通知识库 ↔ 分析任务双向桥接                  |
| V2.0 | 多轮交互式分析，支持用户与智能体 iterative 修订 |
| V3.0 | 团队协作，支持多人共享任务与审批流              |

### 5. 附录

#### 5.1 术语表

| 术语          | 说明                                                       |
| ------------- | ---------------------------------------------------------- |
| LLM-only 策略 | 不预设固定分析方法论，由 LLM 围绕具体问题与数据驱动全流程  |
| G0/GQ/GF      | 三道质量门：G0 摄入门、GQ 逐问门、GF 交付门                |
| RAG           | Retrieval-Augmented Generation，检索增强生成               |
| RRF           | Reciprocal Rank Fusion，倒数排名融合，用于多路检索结果融合 |
| SSE           | Server-Sent Events，服务端推送事件，用于实时进度           |
| Pydantic      | Python 数据验证库，用于定义数据结构                        |
| LangGraph     | 基于 LangChain 的状态图编排框架                            |
| 指标口径      | 业务指标的计算定义、时间窗口、过滤条件与维度过滤规则       |
| 归因拆解      | 将总量变化拆到可解释维度（渠道、地区、用户分群等）的方法   |
